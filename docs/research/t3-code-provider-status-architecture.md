# T3 Code provider status architecture

Research date: 2026-08-17. Source revision: [`pingdotgg/t3code@949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3`](https://github.com/pingdotgg/t3code/tree/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3), the then-current `main` commit. ## Short answer

Yes: T3 has a first-class normalized, event-based provider seam. Every harness implements one `ProviderAdapterShape`—session start/stop, send/interrupt turn, answer approval, answer structured input, resume/read/rollback, and a `Stream<ProviderRuntimeEvent>`—and the orchestration layer projects those events into durable thread state. The sidebar does not read Cursor-, Codex-, or Claude-native states directly. It reads projected session state plus independent pending-approval and pending-input flags. [Adapter contract](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Services/ProviderAdapter.ts#L45-L125)

That separation is the important part to borrow. In particular, an approval does **not** replace `running`: the turn can remain running while `hasPendingApprovals` becomes true, and the UI gives approval higher precedence. This avoids a single mutable status being overwritten by the next assistant/tool event.

## Interface and state layers

T3 ships Codex, Claude, Cursor, Grok, and OpenCode as drivers registered behind the same interface. Unknown drivers degrade to an unavailable snapshot instead of breaking the contract. [Built-in registry](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/builtInDrivers.ts#L1-L52)

Its normalized `ProviderRuntimeEventV2` is a discriminated union covering session, thread, turn, item/content, request, structured input, task/subagent, hook, tool progress, auth/account, MCP, model reroute, config/deprecation, persistence, warning, and error events. [Event vocabulary](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/packages/contracts/src/providerRuntime.ts#L148-L197) [Union](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/packages/contracts/src/providerRuntime.ts#L1139-L1193)

The state vocabularies are deliberately layered:

- Provider session: `connecting | ready | running | error | closed`. [Source](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/packages/contracts/src/provider.ts#L26-L50)
- Runtime session: `starting | ready | running | waiting | stopped | error`; runtime thread: `active | idle | archived | closed | compacted | error`; terminal turn: `completed | failed | interrupted | cancelled`; item: `inProgress | completed | failed | declined`. [Source](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/packages/contracts/src/providerRuntime.ts#L52-L90)
- Orchestration session: `idle | starting | running | ready | interrupted | stopped | error`. [Source](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/packages/contracts/src/orchestration.ts#L288-L309)
- Task/subagent: `pending | running | waiting | idle | completed | failed | cancelled | interrupted`. [Source](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/packages/contracts/src/providerRuntime.ts#L596-L606)
- Sidebar semantic state: `approval | input | working | monitoring | failed | ready`. Approval and input are checked before session running/starting; background liveness is checked afterward. [Source](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/web/src/components/Sidebar.logic.ts#L455-L498)
- Status pills: `Pending Approval`, `Awaiting Input`, `Working`, `Connecting`, `Plan Ready`, `Monitoring`, and `Completed`, with that explicit priority order. [Source](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/web/src/components/Sidebar.logic.ts#L120-L145)

Runtime `waiting` intentionally projects to orchestration `running`; approval/input are separate projected facts, not overloaded lifecycle values. A `turn.started` projects to `running`, `turn.completed` to `ready` (or `error`), and `session.exited` to `stopped`. [Projection mapping](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts#L273-L297) [Lifecycle reducer](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts#L1561-L1609)

## Cursor path

T3 launches `cursor-agent acp`; it does not launch the interactive TUI and scrape its terminal. [Spawn arguments](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/acp/CursorAcpSupport.ts#L33-L70)

The Cursor adapter then:

1. Starts or resumes the ACP session, supplies T3's MCP HTTP server, emits `session.started`, `session.state.changed(ready)`, and `thread.started`. [Session setup](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CursorAdapter.ts#L534-L558) [Ready events](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CursorAdapter.ts#L890-L910)
2. Emits `turn.started` immediately before `session/prompt`, then `turn.completed` from ACP's prompt result. That supplies exact working/ready boundaries without keyboard or text inference. [Turn lifecycle](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CursorAdapter.ts#L916-L967) [Completion](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CursorAdapter.ts#L1013-L1057)
3. Parses ACP `session/update` into assistant-item boundaries, assistant text deltas, plans, and typed tool-call updates; tool kinds/statuses become canonical item types and `item.updated | item.completed`. [ACP parsed events](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/acp/AcpRuntimeModel.ts#L83-L111) [Update parser](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/acp/AcpRuntimeModel.ts#L508-L581) [Canonical tool mapping](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/acp/AcpCoreRuntimeEvents.ts#L32-L76)
4. Handles Cursor extensions separately: `cursor/ask_question` emits `user-input.requested/resolved`; `cursor/create_plan` and `cursor/update_todos` emit plan events. [Cursor extensions](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CursorAdapter.ts#L573-L665)

### Approval flow

ACP calls `session/request_permission`. In full-access mode T3 selects an allow option immediately. Otherwise it allocates a stable request ID, stores a deferred response, emits canonical `request.opened`, waits for the UI decision, emits `request.resolved`, then returns the ACP outcome. [Cursor approval handler](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CursorAdapter.ts#L666-L735)

ACP permission kinds normalize as `execute -> exec_command_approval`, `read -> file_read_approval`, edits/deletes/moves -> `file_change_approval`, otherwise `dynamic_tool_call`. [Canonical request mapping](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/acp/AcpCoreRuntimeEvents.ts#L27-L45) Decisions normalize to `accept | acceptForSession | decline | cancel`, then map back to ACP `allow-once | allow-always | reject-once` (or cancellation). [Decision vocabulary](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/packages/contracts/src/orchestration.ts#L130-L140) [ACP response mapping](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/acp/AcpAdapterSupport.ts#L46-L55)

`request.opened/resolved` project into durable `approval.requested/resolved` activities and pending-approval rows. The shell snapshot exposes `hasPendingApprovals` and `hasPendingUserInput`; the sidebar resolver consumes those flags before lifecycle status. [Activity projection](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts#L362-L425) [Shell contract](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/packages/contracts/src/orchestration.ts#L471-L482) [Sidebar consumption](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/web/src/components/Sidebar.tsx#L806-L887)

## Codex path

T3 spawns `codex app-server`, performs the required `initialize`/`initialized` handshake, then calls `thread/start` or `thread/resume` using the provider thread ID from the stored resume cursor. A recoverable resume failure truthfully falls back to a fresh thread. [Launch](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L893-L946) [Handshake and open](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1736-L1765) [Start/resume selection](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L458-L495) This matches Codex's documented app-server lifecycle: thread and turn APIs plus streamed `thread/*`, `turn/*`, and `item/*` events. [Official Codex app-server protocol](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md#lifecycle-overview)

The adapter maps native notifications rather than inferring terminal text:

- `turn/started` and `turn/completed` update the live provider session and normalize to `turn.started`/`turn.completed`; item lifecycle, assistant/reasoning deltas, tool progress, thread metadata/state, MCP, warnings, and errors normalize into the same runtime union used by every provider. [Native session reducer](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1438-L1488) [Canonical mapping](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexAdapter.ts#L762-L1613)
- Native approval methods (`item/commandExecution/requestApproval`, file-read/file-change, legacy apply-patch/exec-command, dynamic tool) allocate request IDs and wait on a deferred response. They normalize to `request.opened`; the recorded decision or `serverRequest/resolved` normalizes to `request.resolved`. [Native request handlers](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1490-L1600) [Canonical request mapping](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexAdapter.ts#L795-L923)
- `item/tool/requestUserInput` is not treated as an approval. It becomes `user-input.requested`, carries typed questions, waits for `respondToUserInput`, and emits `user-input.resolved`. [Native input request](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1602-L1644) [Response](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1937-L1963)
- Sending a turn calls `turn/start`; interrupt, history reload, and rollback call `turn/interrupt`, `thread/read`, and `thread/rollback`. MCP is configured on app-server and its catalog is reloaded before a turn. [Turn and management calls](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1801-L1906)

## Claude path

Claude also uses the common adapter, but its native transport is the official `@anthropic-ai/claude-agent-sdk`, not a JSON-RPC app server. T3 opens a long-lived streaming `query()` over an async prompt queue, points the SDK at the selected Claude Code executable, enables partial messages, supplies its MCP HTTP server, and consumes typed `SDKMessage` values. [SDK transport](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L1-L21) [Query options](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L4131-L4191)

The Claude adapter synthesizes the same canonical facts from SDK messages:

- It emits `session.started` and `session.state.changed(ready)` when the SDK query is established. The durable Claude `session_id` becomes `thread.started`; `sendTurn` emits `turn.started` before queuing the SDK user message, and an SDK `result` emits `turn.completed`. It also creates a synthetic turn for background assistant output that arrives between user turns. [Session lifecycle](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L4282-L4339) [Turn start](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L4356-L4458) [Turn completion](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L2200-L2377)
- Partial assistant/thinking blocks, tool uses/results, file and command tools, plans, tasks/subagents, usage, rate limits, and stream/process errors are converted to canonical content, item, task, usage, warning, and error events before orchestration sees them. [SDK-message dispatcher](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L3071-L3421)
- The SDK's `canUseTool` callback becomes an addressable approval: T3 emits `request.opened`, waits for `respondToRequest`, emits `request.resolved`, and returns allow/deny plus session-scoped permission updates to Claude. [Approval bridge](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L3949-L4108) `AskUserQuestion` is routed separately through `user-input.requested/resolved` with structured questions and answers. [Structured input bridge](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L3810-L3947)
- T3 resumes by passing the persisted Claude session ID as the SDK `resume` option. Its resume cursor also records the last assistant UUID and turn count for bookkeeping; the provider invocation itself resumes by session ID. The in-memory adapter snapshot contains events seen during this runtime, while T3's durable orchestration projection supplies the already-persisted prior UI history after reload. [Resume cursor](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L659-L695) [Resume option](https://github.com/pingdotgg/t3code/blob/949feb61e4bfd96669ba0e8cf3dca7c6d7f885b3/apps/server/src/provider/Layers/ClaudeAdapter.ts#L4163-L4178)

Cursor ACP, Codex app-server, and Claude Agent SDK therefore differ only below their adapters. All three emit `ProviderRuntimeEvent`, and all three approvals and structured-input requests reach the same projector and sidebar precedence rules.

## Comparison with Soloe

Soloe already has useful pieces, but they are split across interactive TUI and worker execution paths:

- The normal interactive Cursor session launches `agent` as a PTY/TUI, without `acp`. [`SessionCommandBuilder.ts`](../../electron/sessions/SessionCommandBuilder.ts#L264-L290)
- Its interactive status therefore infers `working` from Enter submission and approval from known terminal strings. [`PtyManager.ts`](../../electron/terminal/PtyManager.ts#L309-L340) [`PtyManager.ts`](../../electron/terminal/PtyManager.ts#L646-L672)
- Soloe separately has a genuine Cursor ACP worker adapter and a good native-event normalizer: `session/request_permission -> waiting_for_approval`, Cursor questions -> `waiting_for_input`, message/tool/plan/session updates -> normalized kinds/states. [`CursorEventNormalizer.ts`](../../electron/agents/CursorEventNormalizer.ts#L3-L58)
- That ACP path is worker-only and cannot currently route an interactive approval decision: it auto-approves when configured, otherwise returns `cancelled`; other interactive agent requests return `-32601`. [`CursorWorkerAdapter.ts`](../../electron/agents/CursorWorkerAdapter.ts#L137-L177)
- Interactive Codex launches the normal `codex` TUI (or `codex resume <thread-id>`), and interactive Claude launches the normal `claude` TUI (`--session-id`, `--resume`, or `--continue`). Neither path uses Codex app-server or the Claude Agent SDK. [`SessionCommandBuilder.ts`](../../electron/sessions/SessionCommandBuilder.ts#L195-L262)
- Their best status signals are native **command hooks**, delivered out of process to Soloe: both map prompt submission, pre/post tool use, permission request, stop, and session start into observer states; Claude additionally maps notifications, failures, compaction, subagent stop, and session end. [`HookInstaller.ts`](../../packages/domain/src/integrations/HookInstaller.ts#L67-L88) [`AgentHookDispatcher.ts`](../../electron/agents/AgentHookDispatcher.ts#L563-L613) [`AgentHookDispatcher.ts`](../../electron/agents/AgentHookDispatcher.ts#L691-L726) This is event-based observation, but it is not a bidirectional provider protocol and does not carry T3-style turn/item/request identities.
- Approval text scanning in the PTY is a fallback for all three interactive providers. Hook `PermissionRequest` is more authoritative for Codex/Claude, but the pending approval is still one observer state; any terminal input marks it answered, rather than resolving a particular request ID with a typed decision. [`PtyManager.ts`](../../electron/terminal/PtyManager.ts#L362-L371) [`PtyManager.ts`](../../electron/terminal/PtyManager.ts#L557-L593) [`AgentHookDispatcher.ts`](../../electron/agents/AgentHookDispatcher.ts#L247-L279)
- Claude notifications can mark a generic `waiting_for_input`, but Soloe does not persist the question schema or expose a `respondToUserInput(requestId, answers)` path for interactive Claude. Interactive Codex has no equivalent structured-input bridge. [`AgentHookDispatcher.ts`](../../electron/agents/AgentHookDispatcher.ts#L639-L662)
- Codex and Claude workers are also not first-class protocol adapters: Soloe optionally imports a package, guesses a `query/run/execute` function, and maps arbitrary event type strings by substring. It has no provider-specific approval response, structured-input response, or resume protocol there; missing optional packages fail the worker. [`AgentRuntimeManager.ts`](../../electron/agents/AgentRuntimeManager.ts#L202-L240) [`AgentRuntimeManager.ts`](../../electron/agents/AgentRuntimeManager.ts#L242-L291)
- Soloe's shared observed state is one value (`starting | idle | working | running_tool | waiting_for_input | waiting_for_approval | usage_limited | completed | failed | exited`) stored on one snapshot, and the UI derives its dot/animation directly from that value. [`sessions.ts`](../../shared/types/sessions.ts#L77-L87) [`AgentObserverManager.ts`](../../electron/agents/AgentObserverManager.ts#L112-L143) [`session-status-presentation.ts`](../../src/lib/session-status-presentation.ts#L33-L105)

The practical difference is not that Soloe lacks normalization—it already normalizes Cursor ACP well. It is that the interactive session surface does not use that ACP adapter, and its UI model makes lifecycle/approval/input mutually exclusive snapshot states. T3 instead keeps a shared canonical event log and projects orthogonal facts:

| Provider | T3 native transport and exact events | Soloe interactive path | Soloe worker path |
|---|---|---|---|
| Cursor | ACP; prompt, update, permission, and completion events | TUI; Enter/output/hook inference | ACP with Cursor-specific normalizer |
| Codex | app-server; `thread/*`, `turn/*`, `item/*`, JSON-RPC requests | TUI plus native command hooks and PTY fallback | optional generic SDK reflection and substring mapping |
| Claude | Agent SDK; typed `SDKMessage`, `result`, `canUseTool` | TUI plus native command hooks and PTY fallback | optional generic package reflection and substring mapping |

| Cross-provider concern | T3 | Soloe today |
|---|---|---|
| Working boundary | canonical `turn.started` / `turn.completed` | Codex/Claude hook events; Cursor Enter/output inference |
| Approval | addressable `request.opened/resolved`, orthogonal to lifecycle | single `waiting_for_approval` observer state; response inferred from terminal input |
| Structured input | addressable `user-input.requested/resolved` | generic waiting state at most; no question/answer protocol for interactive Codex/Claude |
| Resume/reload | adapter-native resume identity plus durable orchestration projection | TUI resume arguments plus persisted observer snapshot/terminal metadata |
| UI precedence | approval > input > working > failure/background > ready | direct presentation of one observed state plus runtime status |
| Provider seam | all harnesses emit `ProviderRuntimeEvent` | provider-specific hook/TUI/worker paths converge only at observer snapshots |

## What is worth copying

Copy the seam and state projection, not provider-specific conditionals:

1. Promote Soloe's existing normalized Cursor event work into a common harness adapter contract with `start/resume`, `send/interrupt`, `respondToRequest`, `respondToUserInput`, and an event stream—and implement that seam for Cursor ACP, Codex app-server, and Claude Agent SDK.
2. Prefer the native machine protocols for managed interactive sessions: Cursor ACP, Codex app-server, and Claude Agent SDK. Keep each PTY/TUI path as an explicit compatibility mode with truthful hook/inference-based status.
3. Persist open approval/input requests independently from lifecycle status. A tab may be `{ lifecycle: running, pendingApproval: ... }`; presentation chooses approval first.
4. Feed local and remote/sidebar surfaces from that one projected session summary, rather than having terminal, worker, hook, and UI code each infer status.

Because the source is MIT licensed, implementation can reuse it subject to preserving the license notice for copied source. The architecture and vocabulary can also be reimplemented in Soloe's style without importing T3's Effect/SQLite stack.
